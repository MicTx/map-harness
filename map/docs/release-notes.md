# 更新说明写作规则（release What's new）

每版 release 说明的更新段落由模型按本规则撰写，发布器自动拼入双仓 release body。git 历史与任务包只是素材，不是成品：逐条直译提交信息在这里是错误写法。

## 写作契约

1. **谁写、怎么写**：模型在发布前写 `map/release/notes/vX.Y.Z.md`，从「用户会发现什么变了」出发反推条目；同主题的多个提交合并为一条。
2. **极简**：每版至多 7 条，每条一行一句，一屏读完。没有用户可感知的变化就不硬凑条目。
3. **效果导向**：每条 = `**能力名**：` + 一句话效果。写结果不写手段——「图层改名后样式还在」是对的，「重构了图层面板的状态同步」是错的。自检标准：不读代码的人能否看懂这条变化对他意味着什么。
4. **分组**：按需用 `**New**` / `**Changed**` / `**Fixed**` 加粗小节；没有内容的组不出现，组数随版本实际内容增删。
5. **语言**：英文，与安装引导一致。
6. **禁区**：内部代号（任务包 slug、日期代号、脚本名、评审术语）、承诺或计划中的事、未验证的效果、与安装引导重复的内容。

## 格式底线（发布器机器校验）

文件存在即拼入（版本行 → What's new → 安装引导），缺失即跳过，违规拒绝发布：

- 首行必须是 `## What's new`；
- 1..7 条 `- **能力**： 效果` 形态的条目；
- 每条单行 ≤220 字符；
- 不得含 `{{` 占位符或内部日期代号（`YYYY-MM-DD_` 形态）。

机器只兜结构性底线；效果导向与极简的文风由本契约保证，不由脚本评判。

## 首例

`map/release/notes/v0.1.12.md` 为首例：许可证变更、发布完整性两条 Changed，图层样式与交互一致性两条 Fixed。
